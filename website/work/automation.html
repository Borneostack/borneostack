The problem

Someone opens each supplier invoice, types the supplier, dates and amounts into a spreadsheet, and reminds the owner what is due. It is slow, repetitive work, and a mistyped digit or an invoice paid twice is easy to miss.

What we built

A workflow that reads each invoice, pulls out the fields, checks the sums, catches duplicates, files the row and writes the alert. Anything doubtful goes to a person with the reason, so nobody has to trust it blindly. Try the sample with the wrong total, the one with no due date, and the first one twice.

How it works

These are the real steps, the same ones you saw above.

  1. 1. Receive the file

    The file is accepted only if it really is a PDF, JPG or PNG and is under 2 MB. The check looks at the file itself, not at its name.

  2. 2. Read the text

    The PDF is turned into plain text. A file with no text in it, such as a photo of a paper invoice, stops here and goes to a person. It is never guessed.

  3. 3. Extract the fields

    A language model copies the supplier, invoice number, dates, line items, subtotal, tax and total into fixed fields. It is told to leave a field empty rather than guess. It only reads; it never decides whether an invoice is right.

  4. 4. Check in plain code

    Ordinary code, not the model, checks that the required fields are there, that each line multiplies out, that the lines add up to the subtotal, that subtotal plus tax equals the total, that the dates make sense and that the currency is Ringgit. It also works out whether the invoice is overdue, due within 7 days, or later.

  5. 5. Look for a duplicate

    Supplier plus invoice number is compared with the rows already in your ledger, ignoring capitals, spaces and punctuation.

  6. 6. File the row

    A clean invoice becomes a row in the ledger. Anything doubtful becomes a row marked Needs review, with the reasons. A duplicate is not filed again. The row belongs to your browser only. The file itself is never stored.

  7. 7. Write the alert

    The short message a manager would get, with the supplier, amount and due date, or the reasons for a review. It is written by code from the checked fields. For the sample invoices it is sent to a demo Telegram chat, a few times a day at most; a file you upload is never sent anywhere.

Not tied to these tools

This version is built from custom code because that can run inside a free allowance. The same flow can be built in n8n, Make or another automation tool your business already uses. For a client we pick whichever you can keep running and understand.

How it was checked

On 27 November 2026 we ran all 8 sample invoices through the live system and compared the fields the model returned with the values printed on each invoice. For the 7 invoices that contain text, 63 of 63 fields were right (9 fields each: supplier, invoice number, both dates, currency, subtotal, tax, total and the number of lines). The workflow did what each invoice was meant to make it do in 8 of 8 cases, and the eighth, a photo with no text in the file, was sent to a person as intended.

This is a small test, not a blind one. The first run found the model inventing a subtotal for an invoice that prints only a total, so we tightened its instructions and ran again; the 8 invoices above are the ones we tuned on. Real invoices are messier than these, so a client project starts by testing the workflow on a batch of the client’s own invoices.

One run took about 8.4 seconds on average, almost all of it the model step. When the free daily allowance for the demo runs out, the page switches to recorded runs.

What this example does not do

  • It does not read scans or photos. A file that cannot be read is never guessed, so it goes to a person. A client build can add text recognition (OCR) for scans.
  • It reads one invoice per file and expects Ringgit. An invoice in another currency is sent to a person.
  • It is not connected to a real inbox, spreadsheet or accounting system.
For technical readers: the stack and the limits

One Cloudflare Worker, called straight from this page, with a D1 database for the ledger and Workers AI for the two reading steps. Everything runs inside Cloudflare’s free plan.

Receive: a file is accepted only if its first bytes say PDF, JPG or PNG and it is under 2 MB. The upload must declare its size, and the Worker stops reading at the cap. Each visitor can run 5 invoices in 10 minutes and 15 a day.

Read: env.AI.toMarkdown converts the PDF. Reading a PDF inside the Worker would use more than the 10 ms of processor time the free plan allows, so the Worker only hands the file over and waits. Cloudflare lists this conversion as free for PDFs.

Extract: IBM Granite 4.0 H Micro (@cf/ibm-granite/granite-4.0-h-micro) answering to a fixed JSON schema. A run costs about 3.56 Workers AI neurons on average. The free allowance is 10,000 neurons a day for the whole Cloudflare account, shared with the other examples.

Privacy: the session id travels in a request header, never in a URL. Ledger rows are keyed by a hash of it. Rows are hidden after 24 hours and deleted by the next run or the daily job, so within two days. No IP address is stored.

Alert: posted to Telegram only for the built-in samples, at most 5 messages a day in total and each sample once per visitor per day, and only when a bot is connected.

What a client project adds

  • Your inbox as the starting point: invoices that arrive in Gmail or Outlook are picked up without anyone uploading them.
  • Your spreadsheet or accounting system as the destination: Google Sheets, Excel, or an export your accountant already uses.
  • Your own rules: approval limits, a list of known suppliers, purchase order matching, your tax and rounding conventions.
  • The alert in the place your team reads: a WhatsApp or Telegram group, email, or a task in the tool you use.
  • Scanned invoices and photos, by adding text recognition (OCR), which this example does not run.
  • Running costs on your own accounts. This example runs on free allowances.
